# 命令行评审方案

参考命令行最佳实践（clig.dev《Command Line Interface Guidelines》，十六节；脚本部分另参 Google Shell Style Guide）与我们的用法（判据要靠退出码与 JSON 读结果）制定。

## 用途与用法

评一条命令行的三处，用同一份清单：**规格**（文档写没写清）、**测试**（硬要求有没有对应用例）、**实现**（真跑得住不住）。落在实验室到平台那条流程的两个闸门——文档定稿、代码验收，各按它过一遍。

分两档：**硬**不过就挡住；**软**记下来留到下一轮。定硬的标准有两条——判据与脚本要读它（退出码、JSON、幂等），或者改起来代价大（命名、兼容）。

## 名字与命令面

- 硬：程序名小写、短、好打；子命令用「名词加动词」，同级同名同义（同一个动作用一个写法，不一处 `--done` 一处 `--mark`）。查法：对着 `api-references` 的命令表人工过一遍。
- 硬：不留兜底子命令（省略子命令就干最常用的那件事）。查法：不带子命令直接跑，看它是不是在猜。
- 软：命令面按对象分组（工作流、任务、材料各一族），不按动作堆平。

## 参数与默认值

- 硬：凡是会影响结果的东西，要么在命令行上显式给出，要么能被看清楚（环境变量、上下文文件），不许藏在「你现在在哪」。查法：同一命令换个目录跑，结果不该变。
- 硬：写入型动作要有 `--dry-run` 或等价的预演，且预演不落盘。查法：预演后 `git status` 无变化。
- 软：长选项优先，短选项只留给高频（`-h`）。软：位置参数只放主体对象（文件、名字），别的用选项。

## 帮助与文档

- 硬：每个子命令都有 `--help`，写清它做什么、给一两个例子、列出选项；`-h` 只表示帮助。查法：逐个 `--help` 看有没有例子。
- 硬：终端版文档与规格同源——命令表、字段、判据在 `api-references` 里能查全。查法：抽查三个动作，看参数是否都写进参考。
- 软：错误信息里给出「下一步敲什么」。

## 输出

- 硬：人读的给人、机器读的给 `--json`；`--json` 出的东西字段稳定、能直接被脚本吃。查法：把 `--json` 结果喂给 `jq` 或 python 读一遍。
- 硬：stdout 只放结果，提示与警告进 stderr；管道里不能混进装饰。查法：`命令 | wc -l` 数的行数应等于结果行数。
- 硬：只读用户显式给的文件（内部状态文件除外），不偷偷读写别处。查法：跑一遍只读命令，`git status` 无变化。
- 软：颜色遵从 `NO_COLOR`、`TERM=dumb` 与 `--no-color`，非 TTY 自动关。

## 错误与退出码

- 硬：成功 0、失败非 0，且失败时有可行动的一句话（哪里错、怎么改）。查法：故意给错参数，看退出码与最后一行。
- 硬：错误不被吞——判据跑的命令失败就必须判不过。查法：把一条判据的命令改坏，看它是否变红。
- 软：最要紧的信息放输出最后（眼睛落在那儿）。软：意外的错误附调试信息与提交入口。

## 幂等与可重复

- 硬：同一命令连着跑两遍，结果一致（只读命令绝不改盘；写入命令重复跑不产生重复内容）。查法：连跑两遍比对结果。
- 硬：记录只增不改的东西要有据可查（时间、谁做的、结果如何）。查法：看流水有没有少记。

## 运行上下文与配置

- 硬：上下文（工作区、数据仓、工作流目录）随这件活落盘，命令里能省但有出处；不许只认全局配置文件。查法：把上下文文件删掉，命令应当明确报「找不到」而不是猜。
- 软：环境变量只用在「一次配置、长期沿用」的东西上（如接口基地址），且命令行给出的优先级更高。

## 健壮性

- 硬：输入早校验、早退出（名字、路径、schema 不合规就挡，不半路崩）。查法：喂坏 YAML 与不存在的路径，看报错是否说清。
- 硬：长任务可中断（Ctrl-C 立刻退，交给人的清理给时限）。查法：长任务中途按 Ctrl-C。
- 软：慢动作给进度提示（先去网络上说话）。

## 向后兼容

- 硬：机器读的输出（`--json` 字段）与退出码不许随手改；要改先加新字段、后废旧的。查法：对比两个版本的 `--json` 字段表。
- 软：人读输出可以改（迭代它才好看）；破坏性变更前先警告一轮。

## 分发与版本

- 硬：能问出版本（`--version`），版本与变更记录对得上。查法：`--version` 与 `CHANGELOG` 头一行对照。
- 软：单文件分发、卸载有说明。

## 与我们流程的接口

硬要求里凡是机器能查的，都该在 `code-implement` 的测试里有用例对应：退出码、`--json` 字段、幂等、dry-run 不落盘、上下文可省但有出处。文档定稿时按本方案逐节过一遍，缺的记成文档缺口；代码验收时按硬要求逐条跑，跑不了的写明为什么跑不了。
