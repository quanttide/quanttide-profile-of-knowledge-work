# 实验室到平台

（草案，先讨论设计，定了再写 YAML）

## 路线

实验室（`examples/default/`，Python 写的 kg 原型）的代码已经配了初步文档，结构与平台的基本一致，但这段维护过程很乱。往上走的路子是把这套做法扶正：**先按平台的结构把文档再维护一次，再照文档设计测试、验证测试真的在验业务，最后才写实现代码**。文档驱动加测试驱动，终点是平台上真能用的能力。

目标仓是 `apps/qtcloud-work/src/cli`：Rust + clap，命令行这条骨架的形状与实验室的框架一致（子命令、JSON 输出、版本与变更脚本都在），实现语言与实验室不同（Python 对 Rust），且它自述为**纯服务端客户端**——只对接 provider 的 HTTP 接口，不读写本地文件。

## 三步

**一、再维护文档。** 把实验室那套初步文档按平台的结构重写一遍：字段、动作、判据、命名、边界分别写清，写成一页能当规格用的东西。这一步只碰文档，不碰代码。平台侧是服务端客户端，文档写的是命令面与接口契约，不是文件布局。

**二、照文档设计测试。** 文档里每一条要求对应一条测试，测试写在目标仓里（Rust 的 `cargo test`，落在 `apps/qtcloud-work/src/cli/` 下）。设计完还要验一遍测试真的在验业务：文档条目与测试条目双向对账，一条要求不能没有测试、一条测试不能没有出处；并且测试在实现缺席或实现写错时必须是红的，不接一个恒绿的空壳。

**三、开发代码。** 实现让测试变绿。测试与文档这一轮不动；要改，从文档改起，再改测试，再改代码。

## 产物

每一步都有自己的产物：再维护后的文档（规格）、文档与测试的对账表、测试代码与一次红的记录、实现代码与绿的结果。草稿先落草稿区（`data/context/qtcloud-work/`），人接收后进正式仓。

## 待你拍板

1. **文档正本放哪**：实验室的 `examples/default/docs/` 就地整理，还是搬进领域的 `docs/specification/`，或者直接落在 `apps/qtcloud-work/src/cli/` 自己的文档里？平台侧是客户端，正本放客户端仓还是领域规格仓，影响后面谁来改。
2. **纯服务端这条边界怎么处理**：实验室的 kg 是本地文件驱动（读 YAML、跑判据、写报告），平台 CLI 不读写本地文件。文档再维护时，是以实验室的本地行为为准写成「平台也要读写本地文件」，还是把本地那部分留在实验室、平台只写命令面与接口契约？这决定第二步的测试怎么打——对接真服务端、还是 mock、还是先只测命令面与参数校验。
3. **「测试真的在验业务」怎么算**：文档条目 ↔ 测试条目双向对账（机器可核），加一条「空实现下测试必须红」的记录（人或机器看）？还是另有更强的手段（如故意改坏实现看测试变红）？
4. **闸门几处**：文档定稿一处、测试定稿一处、代码验收一处，还是只在最后收一次口？
5. **一轮的范围**：一次扶正一处能力（如工作流定义、任务、材料四字段），还是十处一起？
